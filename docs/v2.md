Este arquivo é o **âncora de produto** para funcionalidades que não fazem parte do MVP imediato, mas cuja **estrutura de dados já pode ser preparada** sem quebrar o comportamento atual.

## V2 — Monitoramento completo de grupos

### Objetivo

Para fontes `tipo = group`, persistir **todo** tráfego relevante: remetente (JID/número), tipo de mensagem, citações, menções, mídias no MinIO com prefixo por fonte, e metadados brutos suficientes para reconstruir contexto depois.

### Tipos de mensagem (extensível)

Os valores são **strings** no banco (não ENUM SQL), para aceitar novos tipos sem migration:

`sistema sugerido (inicial):` texto, áudio, imagem, vídeo, documento, figurinha, localização, contato, enquete, reação, url, desconhecido, outro.

Novos tipos podem surgir da Evolution/API; gravar como `desconhecido` ou `outro` com `metadata` completo até mapearmos.

### Pipeline de enriquecimento (futuro)


| Ativo  | Etapa                               | Fallback                        |
| ------ | ----------------------------------- | ------------------------------- |
| Áudio  | Transcrição Whisper (local)         | NeuronAI / provedor configurado |
| Imagem | (sem OCR local confiável no início) | LLM visão via NeuronAI          |
| Texto  | Classificação / categorias          | **Base Hub:** `AiRouterService` + `POST /iara` prontos; fase atual já executa classificação textual profile-driven em `message_logs` |

**Estado atual (2026):** stack de inferência (`neuron-core/neuron-ai`, Ollama→Groq→Anthropic→OpenAI, gateway `/iara`, logs `ai.completion`) está descrita no [SPEC.md](../SPEC.md) e no [LLM.md](../LLM.md). Nesta fase, o pipeline é **text-first**: mídia/anexos sem texto ficam em estados pendentes (`pending_media_processing`/`pending_text_extraction`) para futura etapa de **content extraction**, sem encerrar processamento de forma terminal. Itens sem profile ficam em `skipped_no_profile` (terminal operacional até ajuste da source).


Campos dedicados na tabela de mensagens (`transcription_`*, `vision_*`, status de processamento) permitem retries idempotentes e auditoria **sem** misturar tudo em JSON opaco.

### Armazenamento S3 / MinIO

- Bucket compartilhado (`pessoal`), **prefixo por fonte monitorada** (`monitored_sources.media_storage_prefix`).
- Anexos em tabela própria (`message_attachments`) com `storage_path` = chave no bucket.
- Evolução futura: política de lifecycle por prefixo (não depende do MVP).

## V2 — Dashboard e permissões por grupo

**Estado atual (hub autenticado):** o **`/dashboard`** exibe cards com atalhos para cada módulo (config `hub_dashboard.php`); o menu superior repete as mesmas rotas. Novas áreas devem atualizar **ambos** até eventual decisão de simplificar (ver [LLM.md](../LLM.md) *Dashboard e navegação do hub* e [SPEC.md](../SPEC.md) *Dashboard principal*).

### Personas

- **Dono global (Raphael):** acesso a pessoal + todos os grupos monitorados + configurações sensíveis.
- **Admin de grupo (futuro):** acesso ao dashboard **somente** dados ligados a uma ou mais fontes `group` específicas (ex.: moderar leitura de histórico/mídia daquele grupo).

### Modelo de dados (preparação)

- `users.global_role`: `super_admin` | `member` — define se o usuário pode operar em escopo global (super_admin) ou apenas no que for explicitamente concedido (`member`).
- `monitored_source_user`: vínculo N:N entre usuário e fonte monitorada, com papel no contexto daquela fonte (ex.: `group_admin`, `viewer`).

A **V1** pode ignorar totalmente o pivot: só você existirá como `super_admin` via seeder/manual. A existência da tabela **não quebra** o app.

### Autorização no código (quando implementar)

- Gates/policies checando `global_role === super_admin` OU existência de registro em `monitored_source_user` com papel adequado para a rota recurso.

## Como evoluir sem quebrar a V1

1. **Novas colunas opcionais** com default / nullable — ok.
2. **Novas tabelas** referenciando as existentes — ok; código antigo não as usa.
3. **Evitar** renomear colunas em uso; se inevitável, migration de renomeação + janela de deploy.
4. **Feature flags** (.env) para ativar Whisper, LLM visão, ou UI de “admin de grupo” quando estiver pronto.

## Estado operacional antes da fase produto WhatsApp

- A etapa atual fecha a **administração mínima** sem depender de SQL/tinker:
  - `analysis_profiles` com CRUD mínimo em `/hub/analysis-profiles` (entidade continua banco-driven);
  - `monitored_sources` com CRUD mínimo em `/hub/monitored-sources` (inclui associação/troca de profile e notas);
  - dashboard Threads mantido funcional, com fragmentação de view para manutenção.
- Limite intencional desta fase:
  - não inclui experiência completa de produto WhatsApp monitorado;
  - não inclui editor avançado de schema/profile;
  - não inclui modelo completo de permissões por operador/grupo (`monitored_source_user` segue para etapa futura).

## Álbuns de mídia — estado atual vs. Fase F

As fases **A–E** estão implementadas. Refinamentos posteriores (listagem completa no viewer/hub, ordenação por arrastar ou número, limites reais de upload com `AlbumUploadLimits` e `max_file_uploads`, ingestão em job `IngestAlbumUploadBatchJob`, exclusão em lote e apagar álbum, revogação que também limpa `contribution_invite_token`, layout em duas colunas e destaque da URL da galeria pública) estão na **[SPEC dos álbuns](album/SPEC_media_albums.md)** (§3.1 e §9) e datados no **[CHANGELOG](../CHANGELOG.md)** (entradas **2026-05-09**, **2026-05-10** — esta última inclui `php.ini`/`nginx` em Docker para uploads e dependências `ffmpeg`/ZIP na imagem PHP).

Para esta feature, o **roadmap V2** continua focado na **Fase F** (ZIP, tags, watermark, FFmpeg, download ZIP); ver [SPEC_media_albums.md §F](album/SPEC_media_albums.md).

## Backlog sugerido (ordem não rígida)

1. Webhook estável + persistência completa grupo + anexos no MinIO.
2. Jobs de transcrição (fila dedicada) com retry e marcação de status.
3. Evoluir profiles/categorias para múltiplos cenários de WhatsApp (triagem, resumo de grupo, leads), reaproveitando a camada profile-driven já ligada aos jobs e ao hub operacional de fontes monitoradas.
4. UI admin por grupo + convites (se necessário).
5. **Álbuns de mídia — Fase F** (ver [docs/album/SPEC_media_albums.md](album/SPEC_media_albums.md) §F): upload ZIP, tags, watermark on-the-fly, thumb/transcode de vídeo (FFmpeg), download ZIP do álbum. As fases A–E já estão implementadas; esta entrada cobre só os recursos avançados pendentes.
